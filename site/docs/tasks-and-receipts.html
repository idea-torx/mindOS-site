Tasks and receipts

Source: README.md in the runtime repository · All docs

In plain words: a task is a to-do that can only have one owner at a time, needs a heartbeat to stay alive, and can’t be called done until a proof file is sealed. Every step is written down.

Lifecycle

Tasks move through claim → heartbeat → receipt → complete (or fail). Every transition is audited. next --claim dispatches by priority, deadline class, aging fairness, and optional critical-path tie-breaking (--prefer-unblocking).

Leases in practice

python3 autopilot.py claim tsk_4f2a --owner hermes --minutes 30   # → lease_epoch: 1
python3 autopilot.py heartbeat tsk_4f2a --owner hermes --epoch 1
python3 autopilot.py renew tsk_4f2a --owner hermes --minutes 45
python3 autopilot.py complete tsk_4f2a --owner hermes --epoch 1 --note "tests pass"

A mismatch fails with lease superseded (held epoch N, current M); reclaim …. leases gives a fleet-wide live view; --all includes expired-but-still-held leases (recovery candidates).

Receipts

Receipts are hash-sealed evidence files (0600 + sha256 in the audit trail). Completion policy requires one, so "done" always carries proof. Failures feed retry budgets and dispatch backoff instead of disappearing.

Dependencies, impact, critical path

blocked-by asks what holds a task; impact walks the DAG downward; critical-path reports the longest unfinished chain — the minimum number of sequential dispatch waves needed to drain the open graph.
